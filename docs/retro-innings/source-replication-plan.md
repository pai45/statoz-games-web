# Retro Innings: source-game replication plan

Updated 20 October 2026. Execute the stages in order in **Future Games Web**. Preserve the current private handheld game as the fallback. This is a plan for source-faithful behaviour, animation and presentation; the current one-over prototype is not the whole source game. This plan supersedes older target-app and generic 16-bit proposals, while retaining their evidence/history.

Source: **Super International Cricket on SNES**, the supplied D2D2t1JfZDk and tn2SvnEA9w4 recordings, saved native screenshots and the preserved manual. Region/revision, native cadence and original code/physics have not been recovered. Treat recording timestamps as recording timestamps. No native-ROM claim is permitted from a video sample.

The immediate correction is [bounce-cue-v1](bounce-cue-v1/reference-evidence.json): the observed white pitch arrow now indicates the existing simulation's actual incoming ground-contact location. Runner stride cadence also uses travelled world distance. These are bounded improvements; they do not complete the remaining animation work.

## Working method for every stage

Build one complete reference-led sequence, compare it beside the source at native size and normal speed, then put it in the app and regress the complete match. Do not generate another broad pack before the representative action works in its intended camera. A frame sheet is evidence, not playable acceptance.

Each feature/action record contains: source title/edition uncertainty, URL, saved file/hash and recording range; observed behaviour; manual statement where applicable; inferred or authored choices; pose order/holds; foot/grip/bat-tip/ball-release/contact anchors; camera/scale; input and event transitions; open issues and acceptance evidence. Keep a feature matrix with **observed**, **documented**, **authored**, **unknown**, and **implemented/verified** as separate fields.

Use REA where its current browser inspection/asset/scenario capabilities help inspect the web build. Keep partial/incomplete captures labelled. REA does not infer SNES button inputs, physics, native frame holds or ROM assets. Use local deterministic tests for scoring, ball ownership and event transitions. The Product Agent's supported Canvas workflow can assist its supported prototype work; production Three.js integration and independent review are separate. The user's local-only review preference remains in force; no private payload goes to an external review service.

## Architecture and integration

Future Games Web owns cricket under **src/features/games/retro-innings/runtime**. Keep simulation/rules, presentation models, animation metadata, rendering, input/console and original audio separate. Establish explicit data for frame holds and event anchors instead of scattered time checks. Preserve one authoritative game state and one input route per action. Do not switch engine or introduce GSAP to drive ball/actor positions independently of the simulation; Three.js already displays the source-style pixel scene.

The app's existing offline host owns game/session validation, account save namespaces, background/pause/dispose and exit. Build the source with **scripts/build-retro-innings.mjs**, then rebuild only its embedded artifact with **scripts/build-game-bundles.mjs --game=retro-innings**. Keep hashes, provenance and prior snapshots. Use the managed **4306 /statoz-games-web** preview, not a temporary next start process reading a shared mutable .next directory. The earlier 8916 access failure is a release-preview defect to avoid repeating.

Do not modify original StatOz apps, Future Sports, other game rules or Flutter bundles during this cricket pass. Flutter can later import explicitly reviewed web-bundle bytes through its existing process; this plan does not authorize that import or a public deployment.

## Review decisions and stopping rules

- An animation passes when its complete visible action works in the match, including contact and recovery. More frames or smoother tweening alone are not acceptance.
- When missing footage affects identity, controls, camera or scope, ask one focused question and continue independent work. Do not invent a source action or imply native behaviour has been recovered.
- Preserve the source-derived private reference pack and previous playable versions. Keep original/licensed replacement assets separate if later needed for public shipping.
- Independent approval remains pending locally per the user's direction. Do not restart exhausted studio correction loops or submit private context to an external provider.
- At each gate record parent/current hashes, what changed, source-vs-authored decisions, actual visual/gameplay evidence and the next named defect. Only call full replication complete once the feature/action matrix and real-device acceptance are complete.

**Immediate next work after the bounce cue:** Stage1's finite mismatch matrix, then Stage3 camera/scale validation and Stage4's single fully reviewed batting loop. Preserve the now-visible bounce and working contact while correcting those larger mismatches. Stage2 is not a licence to skip source/aim behaviour that is still unverified.
